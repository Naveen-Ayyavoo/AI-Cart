## 1. Corrections to Prior Assessment & Previous Overstatements

Independent code, test, script, and Chrome DevTools inspection uncovered the following overstatements or concrete defects in prior reports (`CURRENT_STATUS.md`, `HANDOFF.md`, `RELEASE-FILE-ALLOWLIST.md`, prior conformance draft):

1. **Lighthouse "100/100" Scope & Categories Overstated:** Earlier claims implied broad 100/100 Lighthouse verification across the flow based only on Home, Draft v2 Review, and Discovery Snapshot. Re-auditing 10 live/rendered routes revealed a **real WCAG `2.9:1` contrast failure** (`Accessibility: 96`) on `approval_detail.html` line 74 (`color: var(--tc-warning)` on `#f1f5f9`), plus matching `--tc-warning` text/white badge issues in `evaluation.html` and `pending.html` (all fixed in this audit and re-verified to **100** Accessibility). Furthermore, Chrome DevTools MCP Lighthouse audits measure **Accessibility, Best Practices, SEO, and Agentic Browsing** — **Performance (LCP/INP/CLS) is NOT included** and Lighthouse explicitly warns it cannot verify full WCAG 2.2 AA compliance (AT/screen readers, zoom reflow, focus-ring contrast).
2. **`00_master_tester.html` ("84/84 Real Chrome Tests") Overclaimed:** Inspecting `scripts/build_master_browser_test.py` revealed it injects **static HTML snapshots (`scratch/rendered_pages/*.html`) into `iframe.srcdoc`**, not live Django views; line 146 exempts `.tc-btn-xs`, `.tc-badge-remove`, inputs, and links from its `>=40px` check (not true `>=44px` everywhere); and `detailsToggleOk` (line 180) is computed but omitted from `passed`.
3. **Recovery Panel (`#tc-progress-recovery`) Was Broken at Runtime:** In `templates/base.html`, inline `style="display: flex;"` overrode the HTML `hidden` attribute (causing the 15-second slow-warning banner to show at `0ms`), and clicking `"Cancel & Restore Controls"` announced `"Operation cancelled"` even though `window.stop()` does not cancel an in-flight Django server request. Fixed via `[hidden] { display: none !important; }`, `"Continue Waiting"`, and `"Stop Waiting & Restore Controls"`.
4. **Stale Approval/Proposal UI Leak After Budget Revision:** `proposal_detail.html` still rendered an active Approve form when `proposal.status` was `SUPERSEDED`/`REJECTED`, `approval_detail.html` fell into `"Ready for PayPal Sandbox Checkout"` on `VOIDED`/`PENDING`/superseded states, `pending.html` kept the PayPal redirect link when `contract` was superseded, `ProposalService.create_proposal()` lacked a `policy_report.contract_id == contract.id` check, and `PaymentService.complete_checkout()` did not block pre-capture on superseded contracts. All 5 fixed and covered by new tests in [contracts/tests/test_ux_defects.py](file:///d:/TrustCart/contracts/tests/test_ux_defects.py).
5. **Silent Live Channel3 API Leak in Test Suite & `verify_frontend.py`:** `Channel3Client.__init__` evaluated `api_key or os.environ.get("CHANNEL3_API_KEY")`, causing `Channel3Client(api_key="")` and unmocked tests (`ProductSearchServiceTests`, `ProductDiscoveryViewTests`, `CustomerFacingUIContentHygieneTests`, `verify_frontend.py`) to call `.env`'s live key on internet-enabled hosts (only passing previously in offline sandboxes via `[Errno 11001]`). Also `verify_frontend.py` created orders with `status="PAID"` (rendering `failed.html` instead of `receipt.html`). Both fixed cleanly.
6. **Design System Documentation Mismatch (`MASTER.md` vs `base.html`):** Prior `FD-90` claimed `docs/design-system/ai-cart/MASTER.md` (formerly `docs/design-system/trustcart/MASTER.md`) tokens were enforced in `templates/base.html`; in fact `MASTER.md` contains the UI/UX Pro Max crypto/dark palette (`#F59E0B`/`#8B5CF6`) rejected by [UI-UX-PRO-MAX-ASSESSMENT.md](file:///d:/TrustCart/docs/planning/UI-UX-PRO-MAX-ASSESSMENT.md) in favor of the light retail tokens in `base.html`.
7. **Rule-Count Arithmetic Error Fixed:** Prior draft contained mismatched counts (`79/15/6` in summary vs `89/8/3` in prose). This report enforces programmatic row-count consistency across all 100 rules.

## 3. Reproducible Frontend Rulebook v1.0 Scoring Formula & Tally (`FD-01`–`FD-100`)

### Weighted Formula Specification
Per prompt Section 4, plain PASS count is insufficient. Each rule carries classification weight:
- `MUST` = **3 pts** | `VERIFY` = **3 pts** | `SHOULD` = **2 pts** | `CONTEXT` = **1 pt**
- Multipliers: `PASS = 1.0` | `PARTIAL = 0.5` | `FAIL = 0.0` | `NOT VERIFIED = 0.0` | `NOT APPLICABLE` = excluded from denominator.
- **Unweighted Counts (100 Rules):** `85 PASS`, `11 PARTIAL`, `3 FAIL`, `1 NOT VERIFIED`, `0 NOT APPLICABLE`.
